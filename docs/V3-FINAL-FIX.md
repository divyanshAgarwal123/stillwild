## Reproduction

Before the correction, the numeric fields generated by `range()` in `src/photo/Studio.tsx` accepted finite fractional values even for integer-step controls. The Motion and weather callbacks passed those fractions into preview state, while `src/photo/model.ts` rounded them during saving and sharing.

For example, at time 2 seconds in an 8-second loop, a live motion count of 1.5 has displacement factor approximately 0.7071. Saving/sharing normalizes it to 2, whose displacement factor is approximately zero at that time. Weather cycles have the same mismatch. A valid share should not silently change a setting still displayed by the editor.

## Required change

- Normalize cycle counts to valid integers **before** they enter live preview state, for both the selected photo's motion and all weather effects. Keep the 1–4 bounds and the existing validator consistent. Use the smallest shared helper or callback adjustment appropriate to the current source.
- Add a targeted browser check that enters/pastes a fractional count into both kinds of numeric field, verifies the live control shows the normalized integer, and confirms saved/shared settings and a representative frozen render agree. Check loop boundaries remain smooth.
- Run the unit tests, relevant photo final/render checks, and production build. No unrelated features or broad redesign are needed. Classic source has not changed for this issue, and its completed 27-group regression result remains in the reports.
- Update the QA note, leave the existing local server running and hand back to the supervising session for source packaging/publication. Do not deploy or submit the hackathon entry from this inner task.
